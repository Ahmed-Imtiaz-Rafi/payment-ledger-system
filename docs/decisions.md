# Decision Log

One entry per significant choice: what, what else I considered, why.

## 001: Mobile money wallet as the project scope
- Considered: commercial bank core ledger, a combined system.
- Chose the wallet because it keeps the focus on concurrency, idempotency, and
  failure handling instead of banking rules. Combined scope risks never finishing.

## 002: PostgreSQL over MySQL
- Considered: MySQL, which I already know.
- Chose PostgreSQL for stricter constraints, clearer EXPLAIN ANALYZE output, and
  because it is the modern default.

## 003: MIT license
- Simplest permissive license for a public portfolio project.

## 004: Pin PostgreSQL to version 17 and fix the host port to 5432
- Considered: `postgres:latest` with a random host port, which is what Initializr generated.
- Chose to pin `postgres:17` so the database version can't change under me and
  results stay reproducible, especially for concurrency and load tests.
- Chose the fixed mapping `5432:5432` so DBeaver always connects to the same
  port instead of me looking up a new one on every run.
- Trade-off: if something else on my machine already uses port 5432, the app
  won't start until I change the left-hand number.

## 005: Separate transfers from ledger entries
- Considered: one table holding both the event and the money movements, with the account on the transfer row.
- Chose two tables. A transfer is one business event with exactly one id. Entries are the individual movements, each pointing back to that transfer. Grouping entries by transfer id makes the sum-to-zero check possible.
- Entries get their own id instead of (transfer id, account id) as the key, because one transfer can touch the same account twice, for example a cash-out amount and its fee.
- Direction lives on the entry as a signed amount, which keeps the sum-to-zero check simple. The kind of event (cash-in, send money) lives on the transfer.
- The entries are the source of truth. The transfer's amount is a description that is cross-checked against them.

## 006: The ledger starts at zero, and the funding account may go negative
- Considered: seeding the platform account with a positive starting amount (for example 50,000).
- Chose a sum of zero across the whole system. A positive seed would make the platform account hit its floor and refuse to fund anything beyond it, while zero-sum has no such ceiling.
- The funding account's negative balance mirrors all the money issued into the system.
- Trade-off: the "no negative balance" rule no longer applies to every account, so the CHECK depends on account type (FUNDING at most 0, every other type at least 0).

## 007: Separate FUNDING and FEE system accounts
- Considered: a single platform account for both funding and fee revenue.
- Chose two accounts, because mixing them nets fee revenue against issued money and makes the platform's balance hard to read.
- System accounts are seeded directly into the database and cannot be created through the API.

## 008: PostgreSQL enums for account type, transfer type, and transfer status
- Considered: VARCHAR columns with a CHECK listing the allowed values.
- Chose real enum types so the type itself limits the values and typos are rejected.
- Trade-off: adding a value later is easy (`ALTER TYPE ... ADD VALUE`), but removing or renaming one is awkward. Hibernate will also need an explicit mapping for them.

## 009: Client-generated idempotency key, unique on transfers
- Considered: detecting duplicates by amount and time window.
- Rejected the time window because it blocks legitimate repeat payments, lets late retries through, and has a race condition under concurrency.
- Chose a UUID generated by the client once per intended payment and reused on retries. It is stored on the transfer with a UNIQUE constraint, so PostgreSQL itself rejects a second insert even if two requests arrive at the same instant.
- A repeat with the same details returns the original result. A repeat with different details is rejected as a client error.
- Open: whether uniqueness should be per sender instead of global.

## 010: Fees are entries inside the same transfer, not a separate transfer type
- Considered: a PLATFORM_FEE transfer type.
- Chose to record the fee as its own entry under the cash-out transfer. The fee stays part of the same business event, and the entries remain separate so fees can be reported or refunded on their own.
- Removed PLATFORM_FEE from the transfer type enum.
